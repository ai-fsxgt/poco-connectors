# 结论与建议写作规范

`report.py stats` 会打印一份统计 JSON。`insights.json` 只能依据这份 JSON 来写。

报告读者是公司管理层和 AI 推广负责人，他们关心：

1. Agent 已经进入了哪些业务环节，哪些还是空白
2. 钱花得值不值
3. 下一步该推什么、管什么

## 可信度红线

违反任何一条，报告就失去可信度：

1. **数字**：只引用统计 JSON 里已有的数字，可以四舍五入，不要自己计算新数字。
   - 需要占比时，用 `cost_share`、`runs_share`、`automation_rate` 等字段。
   - 需要上期数据时，用 `previous_cost_usd`、`previous_runs`、`previous_active_users`。
   - `render` 会自动核对文字中的每个数字，找不到出处的会被拒绝，并列出来要求修改。
   - 每个百分比都要写明对应的指标，并与统计 JSON 的字段一致。例如 `runs_change` 只能写成「运行次数环比」，不能写成用户数增长。
2. **人员**：只写统计 JSON 里出现的姓名和部门。
   - 部门显示为「未填写部门」的，就写「未填写部门」。
   - 不能根据工作内容推测某人属于哪个部门、担任什么职务，或负责什么工作。
   - 描述里出现的人名多半是收件人或被提及的人，不是负责人。
3. **禁止预测和估算**：不写收益估算、节省工时、预期效果、目标值，例如「预计月收益 $5000」「目标覆盖 75 人」。
4. **建议的执行者**：只写角色，例如「平台管理员」「任务负责人」「部门负责人」，或统计 JSON 里出现过的部门。不能编造「某某办」「某某室」负责。
5. **禁用指标**：不使用基尼系数、HHI、Z-Score、健康评分、熟练度等级、用户画像这类说法。

## 错误示例

以下都是真实出现过、必须避免的写法：

| 错误写法 | 问题 |
|---|---|
| 「质量部张雨诗负责」 | 张雨诗只是推送收件人，部门也是推测出来的 |
| 「竖炉和轧钢约占企业产能 30%」 | 数据里没有产能信息 |
| 「按行业流失率 30% 推算，可保留收入约 $114」 | 估算和预测 |
| 「目标将自动化率提升至 60%」「预期降低成本 5-10%」 | 目标值和预期效果 |
| 「超额任务走 PMO 审批」「由能源部负责」 | 编造的组织或流程 |

## 写作要求

- 先写结论，再写依据，一句话只讲一件事，不写空话套话。
- 只写有数据支撑的发现。数据不足就少写几条，不要凑数。

## 分析角度

- **业务覆盖**（`coverage`、`uncovered_domains`）：哪些板块和工序已经用起来，哪些核心工序还是空白。空白的工序是推广建议最直接的依据。
- **固化程度**（`automation_rate`、`by_trigger`）：定时任务和 API 集成代表已经融入日常流程，人工对话代表探索和一次性工作。
- **成本**（`top_items`）：钱集中在哪些工作项。注意区分两种情况：
  - 单次成本高的一次性调研或材料制作；
  - 高频运行的定时任务，要看它的单次成本是否合理。
- **稳定性**（`scheduled`）：失败或取消比例高的任务，以及调试分支会话的数量和成本。
- **推广**（`departments`、`new_users`）：
  - 哪些部门有新用户；
  - 哪些高价值场景只有一个人在用，值得复制推广。
- **环比**：变化超过 20% 的指标要解释原因，用工作项和人员的变化来说明。

## insights.json 格式

`render` 会按下表校验条数和字数，超出就拒绝生成，以保证每次报告的版面一致：

| 字段 | 条数 | 每条字数上限 |
|---|---|---|
| `headline` | 1 | 50 |
| `summary` | 2~4 | 100 |
| `highlights[].value` | 2~4 | 100 |
| `actions[].title` | 3~6 | 24 |
| `actions[].evidence` | 同上 | 90 |
| `actions[].action` | 同上 | 90 |

```json
{
  "headline": "一句话总结本期最重要的结论",
  "summary": [
    "2~4 条关键结论，每条带具体数字"
  ],
  "highlights": [
    {
      "ref": "c03",
      "value": "这项应用解决了什么业务问题、为什么值得关注或推广，1~2 句，不重复次数和成本"
    }
  ],
  "actions": [
    {
      "priority": "P0",
      "title": "要做的事",
      "evidence": "触发这条建议的数据",
      "action": "具体怎么做、由哪个角色做"
    }
  ]
}
```

**`highlights`**：2~4 条。

- `ref` 必须取自统计 JSON 的 `highlight_candidates`。卡片上的标题、负责人、部门、次数、成本由脚本自动填写，你只写 `value`。
- 优先选能复制推广、已经稳定运行的业务场景。
- 尽量覆盖不同的业务领域。

**`actions`**：3~6 条，每条必须有 `evidence`。优先级含义：

| 优先级 | 含义 | 处理时限 |
|---|---|---|
| `P0` | 影响生产或成本失控 | 本周内 |
| `P1` | 影响效果或稳定性 | 本月内 |
| `P2` | 推广和优化 | 无固定时限 |
